# M5: 複数交錯点・複数右折車の待ち行列

M1〜M4は「1台の右折車 対 1本の直進レーン」という単純なケースを前提にしていた。
以下は当初後回しにしていたが、実際の交差点では起こりうるので検討・記録する。
（1は実装済み。2, 3は方針決定済みで実装課題なし。4はそもそもスコープ外。）

## 1. 1本の右折レーンが複数の直進レーンと交錯する場合 — 実装済み

右折レーン（曲線）が持つ `cross_lines` が複数の lane_id を持つケース（1本の右折曲線が、複数の
直進レーンと交錯する）。直進レーン側は`cross_curve`が常に単一値と確定している（[[M1_ahead_flag]]）ので、
このM5で対応が要るのは右折レーン側だけだった。

**交錯点の座標自体は元々問題なかった。** `cross_pos`は各直進車が自分のレーン(`lane_name`)一致で
1点だけ引いてキャッシュしている値（[[M1_ahead_flag]]）なので、右折レーン側が何本の直進レーンと
交錯していても、相手の直進車ごとに正しい`cross_pos`が既に一意に決まっている。対応が必要だったのは
右折車側の**判断状態**（`rt_decided`/`rt_target_id`/`rt_target_lock`/`rt_target_cp`）で、これが
スカラー1組（"今ロック中の相手車1台"）だったため、複数の交錯直進レーンを同時に正しく捌けなかった。

### 実装

[[07_RESOLVE_CONFLICT]]・[[03_UPDATE_LANE_ATTRIB]]・[[01_INIT]]に実装。

- `rt_decided`/`rt_target_id`/`rt_target_lock`/`rt_target_cp`を、`cross_lines`と**同じ長さ・
  同じindex**の配列（`i[]@rt_decided` / `i[]@rt_target_id` / `i[]@rt_target_lock` /
  `v[]@rt_target_cp`）に変更。旧`_ARCHIVE/CONFLICT/04_GET_ATTRIBUTE_ADD.vfl`の
  `i[]@my_conflicts` / `v[]@my_conf_pos`と同じ発想（配列で複数交錯を同時に持つ）。
- [[03_UPDATE_LANE_ATTRIB]]：`lane_changed`時に`cross_lines`をキャッシュした直後、同じ長さで
  これら4配列を作り直す（前の交差点の状態を持ち越さない）。
- [[07_RESOLVE_CONFLICT]]のM2は、`cross_lines`の各indexについて**完全に独立に**
  「候補探索 → 初見TTCロック → 判断ラッチ → 居座り防止」のM2ロジック一式をループで回す
  （直進レーンAへの判断とレーンBへの判断が互いに影響しない）。
- 08_STATEが読む`i@yield_conflict`/`f@dist_to_conflict`はスカラーのまま。全indexのうち
  yield中(`rt_decided[idx]==1`)のものだけを対象に、最も近い交錯点までの距離を採用して集約する
  （どれか1つでもyieldなら止まる。距離は一番近いもの＝直近に停止すべき対象）。

## 2. 同じ右折レーンに複数台が並ぶ場合 — 決定：追加ロジックなし

**各右折車がM2のロジックで個別に（独立に）判断すればよい、と決定。** 隊列専用の調整ロジックは作らない。
前の右折車が`yield`で停止していれば後続車は前車検知(`CAR_DETECT`)で自然に止まり、前の車が`go`で
動き出せば後続車も自分の`rt_target`に対して独立に評価すればよい、という前提で確定。
「前の車が`go`になった直後の自分の判定」を特別扱いする必要はない（各車が独立に見ているだけで、
既存のM2の判断ラッチがそのまま機能する）。

## 3. 直進同士・右折同士の交錯 — 現時点では対象外（保留）

**今回のスコープでは扱わない。** 現状の優先ルール（`turn`が違えば直進優先、同格ならid順、
`_ARCHIVE/CONFLICT/05_CONFLICT_DETECT.vfl`由来）の見直しは、信号のない交差点で直進同士・右折同士が
交錯するケースが実際に必要になった時点で改めて検討する。

## 4. 歩行者・自転車

[[right-turn-changelog]]でも触れた通り、今回のスコープは車 対 車のみ。横断歩道の歩行者・自転車との
交錯は`05_HUMAN_DETECT`が別途担当しており、ここでは扱わない。
