# 2026-09-19 交錯点座標のベイク統一

右折車が使う交錯点座標 `rt_target_cp` の取得を、実行時の相手レーン検索からベイク済み配列の直読みへ変更した。あわせて交錯情報を作っているHoudini側のwrangle 2本をヴォルトに取り込み、座標配列を同時に出力するようにした。

## 背景：同じ「交錯関係」が3通りの方法で導出されていた

調査の結果、交錯まわりの属性が互いに独立した3つの経路で作られていたことが分かった。

| 属性 | 付与先 | 導出元 | 重複除去 | 端点除外 | 並び順 |
|---|---|---|---|---|---|
| `cross_lines` | 曲線（右折レーン） | `sourceprim` | あり | なし | 交点の点番号順 |
| `cross_curves` | 直線（直進レーン） | `sourceprim` | あり | あり（`tol`） | 直線上のu順（近い→遠い） |
| `cross_pos` | 両方 | `candidate` 属性 | なし | なし | 交点の点番号順 |

`cross_pos` だけ導出元からして違うため、`cross_lines` とindexが揃わない。実データでも `cross_lines` が3要素なのに `cross_pos` が4要素という行が複数あった（片方だけ重複除去されているため）。

`03_UPDATE_LANE_ATTRIB.vfl` のループは、このズレを実行時に吸収するための後処理だった。相手レーン名をキーに `findattribval` で引き直すことで、並び順に依存せずindex対応を復元していた。

## 変更内容

### 1. ベイク側（新規・追加のみ）

Houdini側にあったwrangleをヴォルトに取り込み、交錯点座標を `cross_lines` / `cross_curves` と同じループ・同じフィルタ・同じソートで出力するようにした。同一ループから出るのでindex一致が構造的に保証される。

- `13_BAKE_CROSS_LINES.vfl` → `v[]@cross_line_pos` を追加（`cross_lines` と同index）
- `14_BAKE_CROSS_CURVES.vfl` → `v[]@cross_curve_pos` を追加（`cross_curves` と同index）

既存属性の内容は変更していないため、再クックしても従来の挙動は変わらない。

### 2. `03_UPDATE_LANE_ATTRIB.vfl`

`rt_target_cp` の構築を、ループ内の相手レーン検索からベイク済み配列の代入に置き換えた。

```c
// 変更前：cross_linesの要素ごとに
//   findattribval（全点の線形探索）→ pointprims → prim
// 変更後：
v[]@rt_target_cp = prim(1, "cross_line_pos", prim0);
```

得られる座標は同じだが、コストが「車1台 × レーン切替ごと × 交錯数N回の全点線形探索」から「レーン数ぶん、ベイク時に1回」へ移った。残ったループは判断ラッチ3本（`rt_decided` / `rt_target_id` / `rt_target_lock`）のゼロ埋めのみ。

あわせて挙動を変えない整理も行った。

- `len(pr) > 0` の3回チェックを1回に統合し、`pr[0]` を `prim0` として変数化
- `inpt` → `lane_pt`、`ci` → `cross_idx` にリネーム
- 「複数対応は未実装」というコメントを修正。相手は直進レーンで `cross_pos` が必ず1要素のため、`[0]` は暫定ではなく構造上正しい選択だった

### 3. `06_CAR DETECT.vfl`

交差車ブランチの `fwd_dot < 0.0`（後方の相手を無視）の判定を、ブランチ先頭へ移動した。`fwd_dot` は分岐前に計算済みで他の条件と独立しているため結果は変わらず、後方の車に対する `lane_name` 取得・`find`・`yield_conflict` 取得を省ける。

## 実行前に必要な作業

**Houdini側で `13_BAKE_CROSS_LINES.vfl` を再クックし、`cross_line_pos` を生成しておくこと。**

この属性が存在しないと `prim()` が空配列を返し、`rt_target_cp` が空になる。VEXの配列は範囲外読み取りでもエラーを出さず既定値を返すため、`07_RESOLVE_CONFLICT.vfl` 側では全ての交錯点が `{0, 0, 0}`（原点）として扱われ、**エラーなしのまま右折判断だけが壊れる**。

確認方法：ジオメトリスプレッドシートで、右折レーンのprimの `cross_line_pos` が `cross_lines` と同じ要素数になっていること。

## 未解決の問題

### 直進車の通過判定が1つの交錯点しかカバーしていない

実データでは直進レーンの `cross_curves` が3要素、つまり1本の直進レーンが3本の右折カーブと交錯する。しかし直進車側が持つ交錯点は単一の `v@cross_pos` だけで、`i@passed` もスカラーである。

`07_RESOLVE_CONFLICT.vfl:113` は

```c
if (point(0, "passed", pt) == 1) continue; // 通過済みの車
```

と、`passed` が立った直進車を**どの交錯点についての通過かを区別せず**全ての右折車の探索から除外している。

想定される失敗シナリオ（手前から交錯点①②③とする。単一の `cross_pos` が①の場合）：

1. 直進車が①を通過し、48フレーム後に `i@passed = 1`
2. ②③で待つ右折車からこの直進車が見えなくなる
3. 右折車は「交錯する直進車なし」と判断して発進
4. 直進車はまだ②③へ向かって走行中 → 衝突

単一の `cross_pos` が③（最奥）であれば全交錯点を抜けるまで `passed` が立たないので安全側に倒れる。どの点がベイクされているかで危険度が変わるため、要確認。

修正方針は右折車側のM5-1と対称にする形になる。

1. `i@passed` を `cross_curves` と同indexの配列へ変更し、交錯点ごとに独立して通過判定する（座標は `14_BAKE_CROSS_CURVES.vfl` の `cross_curve_pos` を使う）
2. `07_RESOLVE_CONFLICT.vfl:113` を、相手直進車の `cross_curves` の中で自分（右折レーン）の `lane_name` が何番目かを引き、その要素の `passed` だけを見る形に変更する

変更は `01_INIT.vfl` / `03_UPDATE_LANE_ATTRIB.vfl` / `07_RESOLVE_CONFLICT.vfl` にまたがる。

### `13_BAKE_CROSS_LINES.vfl` に端点除外フィルタがない

`14_BAKE_CROSS_CURVES.vfl` には交点が曲線の始点・終点に一致する場合を `tol` で弾く処理があるが、13にはない。コネクタが直線に接続しているだけの箇所が交錯として `cross_lines` に混入している可能性がある。`cross_lines` の中身自体が変わる修正になるため今回は保留した。

### 使われなくなる予定のファイル

上記の直進車側の修正まで入れると、`12_POINT_BAKE_CROSS_POS.vfl` と `12_PRIM_BAKE_CROSS_POS.vfl` はどこからも読まれなくなり、`candidate` 属性への依存ごと削除できる。

### ドキュメントの陳腐化

`OVERVIEW/Overview.md` の89行目・126行目は `cross_lines` を `int[]`（`lane_id` の一覧）と記載したままだが、実際は `lane_name` の `string[]` である。
