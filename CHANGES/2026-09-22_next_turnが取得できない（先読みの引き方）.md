# 2026-09-22 next_turnが取得できない（先読みの引き方を接続関係に変える）

`s@next_turn`が空のままで、`07`の左折除外（`i@dbg_n_turnout`）も`0`のまま。
`03_UPDATE_LANE_ATTRIB.vfl`の先読みが、コネクタprimを位置で引いていたのが原因。

## 原因：`nearpoints`の近い順では自分のコネクタが入る保証が無い

```c
foreach (int np; nearpoints(1, "@lane_name=" + s@next_lane_name, @P, 1e9, 8)) {
```

行き先レーンの`lane_name`を持つ点には、**行き先レーン本体の点**と、**別の入口から来た他のコネクタの点**も混ざる（`11_CONNECT_LANE.vfl`が出口点の`lane_name`をコネクタに複製しているため）。

`lane_changed`が立つのはレーンに入った瞬間＝交差点から遠い位置なので、近い8点がレーン本体の点や別方向のコネクタで埋まると、

- 全部が非コネクタ → `conn = -1` で`next_turn`が`""`のまま
- 別入口のコネクタだけ入った → `conn_any`のフォールバックで**別方向のturnを拾う**

どちらもエラーは出ない。点密度と交差点の形で当たり外れが変わるので、「ある交差点では効くのに別の交差点では効かない」という出方になる。

なお`next_lanes`（点属性）は**レーンの全点に乗っている**ので、`findattribval`で1点だけ引いている`next_lane_name`側は問題ない（`15_BAKE_LANE_END.vfl`のコメントは「入口点にだけ書かれる」と書いているが、実際のジオメトリでは全点にある）。`next_turn`だけが空になるのはコネクタの引き方だけが原因。

## 変更内容

### 11：`next_turns`を`next_lanes`と同じループから焼く

車ごとに毎フレーム探すのをやめて、**行き先の候補と同indexのturn配列**をスプライン側に持たせる。`candidates`を作っている内側ループで`turn_out`をそのまま積むので、index一致は構造的に保証される（`KNOWLEDGE/Houdini運用メモ.md`「同じ関係を複数の経路で導出しない」）。

```c
string candidate_turns[];   // candidatesと同index
...
        append(candidates,      lane_name);
        append(candidate_turns, turn_out);
...
setpointattrib(0, "next_lanes", ip, candidates);
if (len(ip_prims) > 0) setprimattrib(0, "next_turns", ip_prims[0], candidate_turns);
```

**prim属性にした理由**：`next_lanes`は11が入口点にだけ書いているのに実ジオメトリでは全点に乗っている＝Houdini側のどこかで配っている。点属性で焼くとその配る処理にも`next_turns`を足さないと、`findattribval`が引いた点で空のまま返る。レーンprimなら03が既に持っている`prim0`から読める。

コネクタprimにも`array(turn_out)`を焼く。コネクタ上の車の`next_lanes`は行き先1本なので、これで本数が揃う（値は自分自身のturn。従来と同じ）。

### 03：選んだindexで引くだけにする

```c
string nturns[] = prim(1, "next_turns", prim0);
i@nt_baked  = (len(nturns) == n);   // 本数が合わなければ11の焼き直し漏れ
if (i@nt_baked) s@next_turn = nturns[next_idx];
```

`next_lane_name`を選んだindex（`next_idx`）を使い回すので、探索そのものが無くなる。

コネクタprimを引くのは**`next_turn == "right"`のときだけ**。交錯情報（`cross_lines` / `cross_line_pos`）はコネクタprimにしか無いので、ここだけは残る。引き方は`prev_lane`（入口の`lane_id`）で絞ってから`next_lane`（行き先レーン名）で確定させる。`next_lane`はそのコネクタの`lane_name`と同じ値で、行き先が同じなら別の入口のコネクタも一致してしまうため、単独では入口を区別できない。

この順にすると、**コネクタの引き当てに失敗しても左折除外は道連れにならない**。従来は探索失敗＝`next_turn`空＝07/06の除外が黙って無効、という一蓮托生だった。

### デバッグ属性

| 属性 | 意味 |
|---|---|
| `i@nt_baked` | `-1`=判定せず `0`=`next_turns`の本数が`next_lanes`と合っていない（11の焼き漏れ） `1`=一致 |
| `i@dbg_conn` | 右折の先読みで引いたコネクタのprim番号。`-1`なら引けていない |

## 確認すること

- **11を再クックする。** `next_turns`が無いと`i@nt_baked`が0のままで`next_turn`は空
- 左折待ちの車の`s@next_turn`が`"left"`になるか
- `i@nt_baked`が0なら、`next_lanes`を全点へ配っている処理が`next_turns`の本数を崩していないか（prim属性なので本来は影響しないが、`next_lanes`側が増えていれば不一致になる）
- 右折車で`i@dbg_conn`が`-1`なら、`rt_lookahead`が立たず交錯情報も取れていない（`i@cp_baked`も見る）
- 右折車の`i@dbg_n_turnout`が1以上になるか、`i@ctrl_src`が3にならなくなったか

## 追記：`next_turn`の除外は`opp_lane`に乗っている相手だけに効かせる

07の候補フィルタは`lane_name == opp_lane`と`next_lane_name == opp_lane`のどちらでも通す（手前のprimにいる後続車を拾うため）。ところが`next_turn`は**次に乗るコネクタ**を指すので、意味が2通りになる。

| 相手の位置 | `next_turn`が指すもの |
|---|---|
| `opp_lane`に乗っている | `opp_lane`から**出ていく**コネクタ ＝ 交錯点を渡るかどうか |
| まだ手前のレーン | `opp_lane`に**入る**コネクタ ＝ 渡るかどうかとは無関係 |

後者に除外を効かせると、「左折で交錯レーンに入り、そのまま直進してくる車」を候補から落とす。`on_opp_lane`（`lane_name == opp_lane`）を条件に足して、`next_turn` / `rt_lookahead` の2行は乗っている相手だけに効かせる。

`turn == "left"` の1行目には条件を付けない。既にコネクタ上にいる相手はどちらで当たっても曲がって出ていくため。
