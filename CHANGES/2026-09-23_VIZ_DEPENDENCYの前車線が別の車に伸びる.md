# 2026-09-23 VIZ_DEPENDENCYの前車線が別の車に伸びる

`21_VIZ_DEPENDENCY`が前車へ張る弧が、たまに検知していない車へ飛んでいた。

## 原因：ptnumはSolverの中で詰められる

`06_CAR DETECT`が書く`i@car_ptnum`は**ptnum**で、Solverの最後にいる`013_KILL_POINTS`が`removepoint`すると、そのフレームの出力では以降の点番号が1つずつ詰められる。VIZはSolverの**出力**（削除後）を見るので、

- 消えた点より後ろにいた前車を指していた車 → 1つ隣の車へ弧が伸びる
- 前車そのものが消えていた場合 → その番号に入ってきた無関係な車へ伸びる

`i@car_ptnum < npoints(0)`のガードは範囲外しか弾けないので素通りする。車が消えたフレームだけまとめて何本か飛ぶ。

境界をまたぐptnumを持っていたのはここだけだった。`ctrl_src==3`は`rt_target_id`をidで引き、`22_VIZ_CROSS_POINT`と`23_VIZ_COLLISION`はベイク座標（`rt_target_cp` / `collide_pos`）を使っている。信号と横断帯マーカーは静止点なので詰められない。

シミュレーション本体には影響しない。`i@car_ptnum`を読む`07`（`lead_headway`）も`08`も`011`も`>= 0`しか見ておらず、**添字として引いているのはVIZだけ**。

## 変更内容

削除で動かない識別子＝`@id`を使う。

```c
// 06_CAR DETECT
i@car_id = -1;                      // リセット
i@car_id = point(0, "id", pt);      // 前車を採用したとき

// 21_VIZ_DEPENDENCY
int lead = haspointattrib(0, "car_id")
         ? findattribval(0, "point", "id", i@car_id) : -1;
if (lead >= 0) { ... }
```

`i@car_ptnum`はSolverの中では正しいのでそのまま残す。**Solverの外から前車を引くときだけ`i@car_id`を使う。**

## 症状：全部の弧がptnum 0に集まる

`car_id`属性が無いと`i@car_id`は0と読まれ、`findattribval(0, "point", "id", 0)`が「id=0の車」を返すので、全車が先頭の1台を指す。**06側が古い（貼り直していない／再クックされていない）**ときにこうなる。

21側は`haspointattrib`で属性の有無を見て、無ければ描かないようにした。黙って全車をid=0に向けるより、線が消えた方が原因に気づける。

貼る順番は **06 → スプレッドシートで`car_id`列を確認 → 21**。`car_id`列があるのに全部0なら、Solverの中の`06`の位置に`@id`が来ていない（POPのidが引き継がれていない）ということなので、そちらを見る。

## 検討して捨てた案

`f@dist_to_car`と突き合わせて、合わなければ描かない案（21だけで閉じる）。ズレた線は消せるが**正しい相手には張り直せない**ので、KILLがあったフレームは該当車の線が落ちる。許容幅も固定にはできず（06が距離を測るのは`010_INTEGRATE`より前なので、1ステップぶん縮む。対向する交差車は両者の速度が和で効く）、速度から作る必要があった。結局ズレを隠すだけなのでやめた。

## 残っている「線が実態と合わない」ケース

これはズレではなく、どれも仕様の読み方の問題。気になったら別途。

- `ctrl_src==3`で`rt_decided`がラッチされたまま候補が消えている間（`clear_frames`=15フレーム）は`rt_target_id`が全部-1になり、止まっているのに線が1本も出ない
- 前車分岐は`06`の検索半径（速度補正込みで40m級）で拾った前車にも張るので、IDMがほぼ効いていない遠方の前車にも線が出る
- `yellow_commit==1`のとき`08`は`ctrl_src=0`のままreturnするので、黄で通過中＝加速している車から信号へ線が伸びる

## 確認すること

- 車が消えるフレームで、前車以外へ弧が飛ばないこと
- `i@car_id`が-1のまま動かない車がいないこと（いれば`@id`がPOP由来で来ていない）
