# 2026-09-21 横断歩道の検知で、グループ構文の `&&` が効いていない問題

`05_HUMAN DETECT.vfl` の歩行者検知が、次の1行で「lane_name一致 かつ 横断中」を絞っているつもりだった。

```c
int ptnum = nearpoint(3, "@lane_name=" + s@lane_name + " && @ped_crossing=1", @P, @search_radius);
```

## 原因：グループ構文に論理演算子は無い

パターン文字列の空白区切りは**和集合**で、`@attr=a b` のように「`=` の右側に値を並べる」構文がある。
そのため `&&` も `@ped_crossing=1` も、`lane_name` の**追加の候補値として読み捨てられていた**。
エラーも警告も出ない。

Houdini 20.5 で実測（pt0=laneA/ped=0 が至近、pt1=laneA/ped=1 が遠方、クエリ点は原点）:

| 渡したパターン | 戻り値 |
|---|---|
| `@lane_name=laneA && @ped_crossing=1` | 0（ped=0 の点。第2条件が無視されている） |
| `@lane_name=laneA && @nosuch=7`（存在しない属性） | 0（同上） |
| `@lane_name=laneA&&@ped_crossing=1`（空白なし） | -1（値の一部になり全滅） |
| `@lane_name=laneA ^@ped_crossing=0` | 1（`^` 除外なら正しく AND になる） |

つまりこのwrangleは、**そのレーンの横断歩道点を歩行者の有無に関係なく返していた**。
後段は前方判定しか見ていないので、本来なら車は横断歩道で常に止まる。
横断歩道で常に止まる挙動が出ていなかったのなら、Houdini側で Input 3 の手前に `ped_crossing` を絞るノードが入っているはず（要確認）。その場合
この条件式は実質デッドコードのまま「絞れているつもり」の見かけだけを作っていたことになる。

## 変更内容：`nearpoints` ＋完全一致の手書きループにする

`06_CAR DETECT.vfl` / `07_RESOLVE_CONFLICT.vfl` と同じ方式に揃えた。

```c
int   ptnum = -1;
float best  = 9999.0;
foreach (int pt; nearpoints(3, @P, @search_radius)) {
    if (point(3, "lane_name",    pt) != s@lane_name) continue;
    if (point(3, "ped_crossing", pt) != 1)           continue;
    vector pp = point(3, "P", pt);   // 型を明示して受ける（distanceの多重定義回避）
    float  d  = distance(pp, @P);
    if (d < best) { best = d; ptnum = pt; }
}
```

- `^@ped_crossing=0` でも書けるが、属性が存在しないと「除外対象ゼロ」で黙ってレーン絞りだけに戻る。再クック忘れで同じ罠を踏むので採らなかった
- 文字列パターンのパースが点ごと・フレームごとに走らなくなる
- 検証：歩行者なし → `ped_ptnum=-1 / ped_crossing=0`、歩行者あり → 至近の ped=0 の点を飛ばして正しい点を返すことを hython で確認済み

Houdini 側で Input 3 を絞っているノードは、これで不要になる（残したままでも二重に絞るだけで害は無い）。

## 関連

- `KNOWLEDGE/VEXの落とし穴.md` に「グループ構文に AND は無い」を追記
- `03_UPDATE_LANE_ATTRIB.vfl` / `04_SIGNAL DETECT.vfl` の `"@lane_name=" + s@lane_name` は単一条件なので AND の問題は無い。ただし値側がパターン扱いである点は同じ（実測で `*` はワイルドカード、空白を含む値は不一致、空文字は0件。`-` は範囲扱いされず安全）
