# 右折 vs 直進 コンフリクト解決仕様（検索コーン＋到達時間方式）

※ このドキュメントは既存の実装（`01`〜`07` の一連のノード群）を前提にしたものではなく、
　 ゼロから組み立てる独立した設計仕様として書く。既存実装とデータ構造が似ていたとしても偶然であり、
　 依存関係はない。

## 0. 目的
交差点において、右折車が直進車を検出し、優先順位（直進＞右折）に従って安全に振る舞うためのロジックを定義する。
あわせて、直進車側が持つべき安全マージン（保険的な減速）についても定義する。

## 1. 前提となるデータモデル

このロジックが成立するために必要なデータを、一から定義する。

- **直線ライン（直進レーン）**：自身と交錯する曲線ラインについて `{lane_id, 交点のワールド座標 cp}` を持つ
- **曲線ライン（右折レーン）**：同様に、交錯する直線ラインについて `{lane_id, 交点のワールド座標 cp}` を持つ
- **車**：
  - 自分が今乗っているレーンの `lane_id`
  - 自分の位置 `P`、進行方向 `dir`、速度 `vel`
  - 種別 `turn`（`"straight"` / `"right"`）

交錯する相手レーンの情報（`lane_id` と交点座標）は多くても数個（5個程度）なので、
車が常時保持し続ける必要はなく、**右折を開始するタイミングで一度だけレーンから取得してキャッシュ**すればよい
（座標も、交錯レーンの`lane_id`と同じタイミング・同じコストで一緒に取得できる。取得コストを理由に座標を避ける必要はない）。
取得後は右折が終わるまでその値を使い回す。座標自体は静的（レーン形状が変わらない限り不変）なので、
毎フレーム取り直す必要はなく、`self.P` の方だけがフレームごとに更新されて距離が縮んでいく。

※ 検討過程で「座標の代わりにレーン弧長distanceのスカラーだけ持てばよいのでは」という案も出たが、
　 それは「毎フレーム座標を検索し直すコストを避けたい」という誤った前提に基づいていた
　 （実際は座標も1回取得してキャッシュすれば同じコストで済む）。弧長方式は
　 カーブ区間での直線距離近似誤差を避けられるという利点はあるものの、
　 車が `dist_on_lane`（レーン上の進行距離）を持っている前提を新たに追加する必要がある。
　 その前提を確認できるまでは、追加の依存が少ない座標方式を基本形とする
　 （弧長方式は 7節 に代替案として残す）。

## 2. 優先順位

直進 ＞ 右折。右折側が譲る。
→ よって **右折車の検索・判定ロジックの方を厳密にする**（直進車側は簡易チェックでよい）。

## 3. 右折車側の処理

### トリガー
右折を開始した段階（右折レーンに入った時点）で、自分のレーンが交錯する直線レーンについて
`{lane_id, cp（交点座標）}` を **一度だけ取得してキャッシュ**する（多くても数個なので、
右折している間はこの結果を使い回せばよい）。そこから直進車の検索を開始する。

### 検索対象の絞り込み
- 候補レーン：上で取得した「交錯する直線レーンの `lane_id` リスト」
- そのレーンの `lane_id` を持つ他車を近傍検索する（検索半径は車線幅から算出する。下記パラメータ表参照）

### 検索コーン（内積による事前フィルタ）
対象車 `other` について、

```
V   = other.P - self.P              // 自分→相手 のベクトル（正規化）
dot = dot(normalize(V), other.dir)  // 相手の進行方向との内積
```

- `dot` が **-0.8 〜 0.1** の範囲に収まる車を候補として残す
  - `dot ≈ -1`：相手は自分の方向へ正面から向かってきている
  - `dot ≈ 0`：進行方向が自分への視線とほぼ直交（＝交錯位置付近を横切っている）
  - `dot > 0.1`：相手は自分から離れていく方向 → 既に通過済みとみなし除外
- ここはあくまで「明らかに無関係な車」を弾くための粗いフィルタであり、最終判断には使わない

### 到達時間の比較（最終判断）
コーンを通過した候補それぞれについて、右折開始時にキャッシュした `cp`（この候補レーンに対応する交点座標）
までの到達時間を比較する。

```
t_self  = dist(cp, self.P)  / max(self.vel_assumed, v_floor)
t_other = dist(cp, other.P) / max(other.vel,        v_floor)

if (t_other < t_self + need_gap) blocked = 1
```

- `cp` はキャッシュ済みの固定値、`self.P` / `other.P` は毎フレーム更新される値なので、
  `dist()` の計算自体は毎フレーム行うが、`cp` を探し直すコストはかからない
- `need_gap`：安全マージン（秒）。相手が自分より先に交点へ来る、かつその差が `need_gap` 未満なら「塞がれている」とみなす
- 自分が停止中の場合、`self.vel` をそのまま使うと `t_self` が発散して永久に出られなくなるため、
  「今出たら何秒で着くか」を想定した最低速度（`v_floor` や、右折時の想定発進速度）で計算する

### 反応
- ブロックする候補が **いる** → `dist(cp, self.P)`（交点までの残り距離）に応じて
  - **4m未満** → 停止
  - **9m未満**（4m以上）→ 減速
  - それ以上離れている → まだ反応不要（次フレーム以降も監視を継続）
- ブロックする候補が **いない** → そのまま進行。むしろ少し急ぎ目（目標速度を一時的に引き上げる）にして交差点を素早く抜ける

## 4. 直進車側の処理

直進車は優先権を持つため、これは「譲る」ロジックではなく、
右折車の飛び出し・誤判定に対する保険的な減速（安全マージン）という位置づけ。

### 検索対象の絞り込み
- 自分のレーンが交錯する右折レーンについて `{lane_id, cp}` を取得（こちらも数個程度なので都度取得でよい）
- その `lane_id` を持つ他車を近傍検索する

### 検索コーン（内積による事前フィルタ）
対象車 `other`（右折車）について、

```
V   = other.P - self.P     // 自分→相手 のベクトル（正規化）
dot = dot(self.dir, V)     // 自分の進行方向との内積
```

- `dot >= 0.9` → 相手がほぼ自分の正面（進行方向のごく狭いコーン内）にいる → 候補とする

### 到達時間の比較（最終判断）
候補について、`cp` までの到達時間を比較する。

```
t_self  = dist(cp, self.P)  / max(self.vel,  v_floor)
t_other = dist(cp, other.P) / max(other.vel, v_floor)

if (abs(t_self - t_other) < safety_margin) → 減速
```

- 単に「正面にいる」だけで減速すると、遠くにいてまだ全く脅威でない右折車にまで反応してしまう。
  到達時間差が小さい（＝ほぼ同時に交点へ来てしまう）場合だけ減速する。

## 5. パラメータ一覧（要チューニング／チャンネル化）

| パラメータ | 説明 | 暫定値 |
|---|---|---|
| 右折車の検索コーン下限 | `dot(V_self→other, other.dir)` の下限 | -0.8 |
| 右折車の検索コーン上限 | 同上限 | 0.1 |
| 直進車の前方コーン閾値 | `dot(self.dir, V_self→other)` の下限 | 0.9 |
| 検索半径 | 近傍探索の距離。車線幅が既知なので、その倍数で算出する（固定のマジックナンバーにしない） | 車線幅ベースで算出（倍率は要検討） |
| `need_gap` | 右折車が「塞がれている」と判定する安全マージン（秒） | 未定 |
| `safety_margin` | 直進車が減速判定する到達時間差の閾値（秒） | 未定 |
| `v_floor` | 到達時間計算に使う最低速度（停止中でも発散させないため） | 未定 |
| `stop_dist` | 交点までこの距離未満なら停止 | 4m |
| `decel_dist` | 交点までこの距離未満なら減速（`stop_dist` 以上） | 9m |
| 急ぎ目係数 | クリア時の目標速度倍率 | 未定（例: 1.1） |

## 6. 疑似コード

```c
// ── 右折車（右折開始の瞬間に1回だけ）──
// 数個程度なので、都度取得してキャッシュすればよい（座標込みで取っても同じコスト）
conflicts[] = 自レーンが交錯する直線レーンの (lane_id, cp) を取得;

// ── 右折車（右折中、毎フレーム）──
{
    int   blocked = 0;
    vector blocking_cp;

    foreach ((o_lane, cp); conflicts) {
        int cars[] = lane_id == o_lane な近傍車を検索(SEARCH_RADIUS);  // SEARCH_RADIUS は車線幅から算出

        foreach (car other; cars) {
            vector V    = other.P - self.P;
            float  cone = dot(normalize(V), other.dir);
            if (cone < -0.8 || cone > 0.1) continue;   // 事前フィルタ

            float t_self  = length(cp - self.P)  / max(self.vel_assumed, v_floor);
            float t_other = length(cp - other.P) / max(other.vel,       v_floor);

            if (t_other < t_self + need_gap) { blocked = 1; blocking_cp = cp; break; }
        }
        if (blocked) break;
    }

    if (blocked) {
        float d = dist(self.P, blocking_cp);
        if      (d < 4.0) stop();
        else if (d < 9.0) decelerate();
        // 9m 以上ならまだ反応しない（次フレームで再評価）
    } else {
        // 通常より少し急ぎ目で進行
    }
}

// ── 直進車（毎フレーム）──
{
    // 自レーンが交錯する右折レーンの (lane_id, cp) を取得（数個程度）
    conflicts[] = 自レーンが交錯する右折レーンの (lane_id, cp) を取得;

    foreach ((o_lane, cp); conflicts) {
        int cars[] = lane_id == o_lane な近傍車を検索(SEARCH_RADIUS);

        foreach (car other; cars) {
            vector V    = other.P - self.P;
            float  cone = dot(self.dir, normalize(V));
            if (cone < 0.9) continue;   // 事前フィルタ

            float t_self  = length(cp - self.P)  / max(self.vel, v_floor);
            float t_other = length(cp - other.P) / max(other.vel, v_floor);

            if (abs(t_self - t_other) < safety_margin) {
                // 減速（安全マージン）
            }
        }
    }
}
```

## 7. 未確定事項

- `need_gap` / `safety_margin` の具体的な秒数（交差点の規模や車速レンジに応じて調整が必要）
- 停止中の車の `t_self` 計算に使う想定速度（発進加速を考慮するかどうか）
- 検索半径を車線幅の何倍にするか（交差点の大きさに対してどの程度余裕を持たせるか）
- 右折車の「交錯レーン + `cp`」の取得を、右折開始の瞬間の1回きりにするか、
  右折中も一定間隔で再取得するか（レーン形状が動的に変わらない前提なら1回で十分なはず）
- **代替案（弧長距離方式）**：`dist(cp, P)` は右折レーン（曲線）区間では直線距離のため、
  実際の走行距離をわずかに過小評価する。もし車が `dist_on_lane`（現在のレーンをどれだけ進んだか）を
  既に持っている、または安価に求められるなら、`cp` の代わりに
  `{lane_id, 自レーン上の交点までの弧長距離, 相手レーン上の交点までの弧長距離}` を持たせ、
  `remain = 弧長距離 - dist_on_lane` で到達距離を求める方式に切り替えるとカーブ区間の精度が上がる。
  ただし `dist_on_lane` という前提を新たに増やすことになるため、それが既存の実装で
  安く手に入るかどうかを確認してから判断する（無ければ座標方式のままで十分な精度のはず）
