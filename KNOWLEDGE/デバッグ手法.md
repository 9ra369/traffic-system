# デバッグ手法

VEXは実行時エラーをほとんど出さないので、**属性として値を書き出して目で見る**のが基本戦略になる。

## 大原則：ロジックより先に配線とクックを疑う

ヴォルト上のVEXが正しくても、Houdini側が以下の状態なら動かない。しかも**エラーは出ない**。

- ベイク用wrangleを再クックしておらず、属性がまだ存在しない
- ノードの入力に想定と違うジオメトリが繋がっている

実例: `07_RESOLVE_CONFLICT`の入力0に車のジオメトリが繋がっておらず、`nearpoints(0, @P, 40)`が別ジオメトリ（6点）を見ていた。候補が常に0件になるので`yield_conflict`が永久に0のまま。`passed`・`lane_name`・`car`チェックを延々と疑ったが、全部その先の話だった。

**着手前に確認すべき2つ**

```c
i@dbg_npoints = npoints(0);   // 入力0の総点数。車の台数と一致するか
```

```c
// 属性が本当に焼かれているか
i@dbg_len = len(prim(1, "cross_line_pos", prim0));
```

## nearpointsが0件なら構造的な問題

`nearpoints(0, @P, r)`は**自分自身（距離0）も返す**。だから結果が0件なら、半径やタイミングではなく、見ているジオメトリが間違っている。

半径を極端に大きくして切り分ける。

```c
i@dbg_n_cands      = len(nearpoints(0, @P, search_radius));
i@dbg_n_cands_huge = len(nearpoints(0, @P, 100000.0));   // 事実上無限
```

`huge`が正の数なのに通常半径で0なら半径の問題。**両方0なら入力ジオメトリの問題。**

## 段階別カウンタでフィルタのどこで落ちているかを特定する

`continue`が連なる候補探索は、どの条件で全滅しているかが外から見えない。段階ごとに数える。

```c
if (point(0, "lane_name", pt) != opp_lane) continue;
dbg_n_lane_match += 1;
if (point(0, "car", pt) != 1)    { dbg_n_skip_car += 1;    continue; }
if (point(0, "passed", pt) == 1) { dbg_n_skip_passed += 1; continue; }
```

計測のために判定順を入れ替えても、`continue`の順序は通過する集合を変えないので結果は同じ。終わったら元の順（安いチェックを先に）へ戻す。

どのカウンタも0なら、そもそもループに入っていない。`len(cands)`を疑う。

## 配列で書き出すときはセンチネルを使う

既存の配列（`cross_lines`など）と同じindexで揃えると、どの要素の話か対応が取れる。

```c
float dbg_margin = -9999.0;   // 評価に入らなかったindexは-9999のまま
...
if (t_id >= 0 && target_pt >= 0) {
    dbg_margin = t_ego + safety_margin - t_other;
}
```

**「計算した結果が0」と「そもそも計算していない」を区別できる**のが重要。`0`で初期化すると両者が混ざって切り分け不能になる。

## 閾値判定は差分を書き出す

boolだけ見ても「どれくらい足りないか」が分からない。

```c
t_lock = (t_other < t_ego + safety_margin) ? 1 : 0;
dbg_margin = t_ego + safety_margin - t_other;   // 正なら成立、負なら不足分が分かる
```

`-1`付近なら`safety_margin`を1増やせば成立する、という読み方ができてチューニングが速い。内訳（`t_other`と`t_ego`）も別々に出すと、どちらが異常かまで分かる。

## Solverの内と外は見えているものが違う

Solverの外側（直後）に置いたデバッグノードと、Solver内部のwrangleでは、参照できるジオメトリの状態が異なる。外側のノードで見つかるのに内側で見つからない場合、両者の入力の違いを疑う。

デバッグ専用ノードは`dbg_`接頭辞で属性名を統一し、本体のロジックに一切影響させない（`DEBUG_CROSS_MATCH.vfl`がその形）。

### Solver内の追加入力は外側には引き継がれない

Solver内のwrangleに繋いでいる信号（Input 2）や歩行者（Input 3）のジオメトリは、**Solverの外側のノードには存在しない**。外側で同じものを参照したければ、そのノードにも同じジオメトリを同じ番号で繋ぎ直す必要がある。

これが効いてくるのが**ptnumを保持している属性**。`i@signal_ptnum`や`i@ped_ptnum`は、それぞれのジオメトリ側の点番号でしかない。番号だけ持っていても、対応するジオメトリが繋がっていなければ`point()`は`{0,0,0}`を返す（エラーは出ない）。

実例: `21_VIZ_DEPENDENCY.vfl`で信号へ線を張ろうとしたら原点へ伸びた。Input 2が未配線だったため。

**対策**: 外側のノードでも入力番号をSolver内と揃える。そのうえで`npoints(n)`で範囲を確認してから`point()`を呼び、解決できなければ何も描かない。描かないこと自体が配線ミスのシグナルになる。

### 点やprimを追加するノードはSolverの中に置かない

可視化のために`addpoint`/`addprim`するノードをSolver内部に置くと、毎フレーム点数が増えてシミュレーション本体が壊れる。必ず外側に置き、生成物は専用グループ（例: `decel_lines`）に入れて分離できるようにする。

## 半径などの定数を複数箇所に持たない

デバッグノードと本体で同じ半径を使う場合、片方だけ変更すると判定が食い違ってデバッグ結果自体が嘘になる。コメントで同期を明示するか、パラメータ化する。
