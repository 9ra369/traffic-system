# Houdini運用メモ

## キャッシュの使い分け

用途の違う2種類がある。

### File Cache SOP（最終的に使うのはこちら）

DOPのSOP側出力（DOP Import、またはDOP Network SOPの出力）の直後に繋ぎ、`.bgeo.sc`の連番で書き出す。書き出し後はLoad from Diskに切り替わり、Houdiniを閉じて開き直しても残る。毎回シミュレーションし直す必要はない。

**注意点**

- DOPシムは先頭フレームから順に流す必要がある。途中フレームへ飛ぶと正しく計算されないので、書き出しは必ず開始フレームから通しで走らせる
- **上流の変更を自動検知しない。** VEXやパラメータを直してもキャッシュがある限り古いファイルを読み続ける。「直したのに挙動が変わらない」はだいたいこれ
- パスにバージョン番号（`v001`, `v002`...）を入れておくと、良い結果を潰さずに済む

### DOP Network ノードのSimulationタブ（作業中用）

- `Cache Simulation` — メモリ上にフレームを保持
- `Cache Memory (MB)` — 足りないと古いフレームが捨てられて再計算が走る
- `Allow Caching To Disk` + `Disk Cache Directory` — メモリに収まらない分をディスクへ

シム内部の状態キャッシュなのでジオメトリファイルとしては残らず、**Houdiniを閉じると消える**。永続するのはFile Cacheだけ。

## 点の削除：removepoint と i@dead

| 文脈 | 方法 |
|---|---|
| SOPのAttribute Wrangle | `removepoint(0, @ptnum)` |
| DOP内のGeometry Wrangle | `removepoint`で動く |
| POP Wrangle | `i@dead = 1;`（ソルバに削除させる） |

エラーメッセージの先頭（例: `popobject - ./geometrywrangle1/geometryvop1`）を見れば、どの文脈で走っているか分かる。

## コネクタは行き先レーンのlane_nameを継承する

`11_CONNECT_LANE.vfl`は、交差点の接続曲線を生成するとき**出口点のlane_nameをコネクタに複製**している。

この帰結として、車が交差点に入った瞬間に`lane_name`は行き先レーンの名前へ変わる。一方、後続車は`u >= 0.99`になるまで手前のレーン名のまま。

つまり**同じ車列にいる車同士でもlane_nameが食い違う期間がある**。lane_nameだけで「同じレーンの前車か」を判定すると、交差点で止まっている前車を見失う。`next_lane_name`も同一レーン扱いにする必要がある（`06_CAR DETECT.vfl`の`same_lane`判定）。

## 1 prim = 1 レーン

スプラインなので1つのprimが1本のレーンに対応し、レーン単位の属性はprim属性として持てる。`pointprims()`の結果が複数になることは基本的にない。

ただし空配列になった場合に`pr[0]`が0になる問題があるので、`len(pr) > 0`のガードは必要（[[VEXの落とし穴]]参照）。

## 同じ関係を複数の経路で導出しない

同じ「交錯関係」を3通りの方法（`sourceprim`ベースが2つ、`candidate`属性ベースが1つ）で別々に導出していたため、重複除去の有無・端点除外の有無・並び順が全部食い違い、配列同士のindexが対応しなくなっていた。

**同じ意味を持つ配列は、同じループ・同じフィルタ・同じソートから同時に出す。** そうすればindex一致が構造的に保証され、実行時に対応を取り直す処理が不要になる。

実例: `13_BAKE_CROSS_LINES.vfl`で`cross_lines`と`cross_line_pos`を同じループでappendしている。

## 「直したのに反映されない」の切り分け順

VFLファイルはノードのミラーなので、**ノード側が古いまま**という状態が普通に起こる。File Cacheを疑う前に、まずここを見る。

1. ノードのコードを丸ごとコピーしてファイルに落とし、VFLとdiffする。属性が1つ出ないだけでも、実際には機能ごと入っていないことがある
2. どのコミット相当かを特定する（`git show <hash>:<file>` と総当たりでdiff）。ずれの幅が分かると、他のどのノードを貼り直すべきかも決まる
3. コードが同じなら File Cache / 先頭フレームからの流し直しを疑う

diffで**VFLに戻していないHoudini側の調整**が見つかることがある（実例: `clear_frames` をノードで15に直してVFLは24のまま）。丸ごと貼る前にその値を先にVFLへ戻す。逆向きに上書きすると、調整したことを忘れて元の値でチューニングし直すことになる。
