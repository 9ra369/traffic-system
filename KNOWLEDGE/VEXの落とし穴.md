# VEXの落とし穴

言語仕様が原因で踏んだもの。エラーが出るものと、**出ないまま黙って壊れるもの**に分けて記載。

## エラーが出るもの

### point() / prim() の戻り値は型が確定しない

`point()`や`prim()`はアクセスする属性の型を静的に決められないため、オーバーロードされた関数へ直接渡すと曖昧になる。

```
Ambiguous call to function dot(). Candidates are:
  float dot(vector4; vector), float dot(vector; vector)
```

```c
// NG: normalizeを挟んでもdotの引数型が決まらない
if (dot(normalize(point(0, "dir", pt)), v) <= 0) ...

// OK: 型を明示した変数で受ける
vector opp_dir = point(0, "dir", pt);
if (dot(normalize(opp_dir), v) <= 0) ...
```

`append()`でも同じことが起きる。`12_POINT_BAKE_CROSS_POS.vfl`に「型を明示して受ける（append曖昧回避）」というコメントがあるのはこれが理由。

**回避策**: `point()`/`prim()`の結果は、いったん型付きのローカル変数で受けるのを習慣にする。

一方、`t_cp - point(0, "P", pt)` のように**左辺の型から推論できる文脈では通る**。だから同じファイル内でも通る箇所と通らない箇所が混在する。

### 配列属性の `[]` は型プレフィクス側に付く

```
Empty array index (84,21)
```

```c
// NG
@cands[]  = cands[];
i@cands[] = cands[];

// OK
i[]@cands = cands;
```

`i[]@`, `f[]@`, `s[]@`, `v[]@` の形。右辺は変数名のみで`[]`を付けない。

## エラーが出ずに黙って壊れるもの

こちらの方が危険。**Houdiniは何も言わずに既定値を返す。**

### 配列の範囲外アクセスは 0 を返す

```c
int pr[] = pointprims(1, pt);
vector cp[] = prim(1, "cross_pos", pr[0]);   // prが空だと pr[0] は 0
```

`pr`が空配列でも`pr[0]`はエラーにならず`0`になる。結果として**prim 0番という無関係なプリミティブの属性を読む**。エラーも警告も出ないので、間違った座標が静かに混入する。

だから `if (len(pr) > 0)` のガードは「クラッシュ防止」ではなく「**無関係なデータを読まないため**」に必要。

### 存在しない属性の読み取りも既定値を返す

`prim(1, "cross_line_pos", n)` で`cross_line_pos`属性が存在しなければ、エラーではなく空配列が返る。

**運用上の最大の罠**: ベイク用のwrangleを追加・変更したあとHoudini側で再クックし忘れると、属性が無い状態で読まれ、`{0,0,0}`や空配列として処理が進む。**エラーは一切出ないのに挙動だけが壊れる。**

実例: `rt_target_cp`が空になると`07_RESOLVE_CONFLICT.vfl`側で全交錯点が原点扱いになり、TTC計算が無意味な値になる。

### グループ構文に AND は無い（`&&` は黙って捨てられる）

```c
// NG: ped_crossing=1 の条件は一切効かない
nearpoint(3, "@lane_name=" + s@lane_name + " && @ped_crossing=1", @P, r);
```

グループ/パターン文字列に論理演算子は無く、空白区切りは**和集合**。`@attr=a b` のように
「`=` の右側に値を並べる」構文があるため、`&&` も後続の条件も**追加の候補値として読み捨てられる**。
存在しない属性を書いてもエラーは出ない。

Houdini 20.5での実測（pt0=laneA/ped=0が至近、pt1=laneA/ped=1が遠方）:

| パターン | 戻り値 |
|---|---|
| `@lane_name=laneA && @ped_crossing=1` | 0（ped=0の点。第2条件が無視されている） |
| `@lane_name=laneA && @nosuch=7` | 0（エラーも警告も無し） |
| `@lane_name=laneA&&@ped_crossing=1` | -1（値の一部になり全滅） |
| `@lane_name=laneA ^@ped_crossing=0` | 1（`^`除外なら正しくANDになる） |

`^`でも書けるが、属性が存在しないと「除外対象ゼロ」で黙ってレーン絞りだけに戻る（再クック忘れと同じ罠）。
**複数条件は`nearpoints`＋完全一致の手書きループにする**（`05_HUMAN DETECT.vfl`、`06`/`07`と同じ方式）。
パターン文字列のパースが点ごとに走らなくなる利点もある。

値側がパターン扱いである点も共通の注意（実測）: `*`はワイルドカード、空白を含む値は不一致、空文字は0件。

### グループ/パターン文字列が空だと絞り込みが効かない

```c
float d = xyzdist(1, s@lane_name, @P, hitprim, uvw);
```

`s@lane_name`が空文字列になると、プリミティブグループの指定が空になって**絞り込みが効かない状態**になりうる。意図したレーン以外にヒットする。

`02_CHANGE ROAD.vfl`で行き止まり（`next_lane_name`が空）のときに`lane_name`を空文字で上書きしてしまい、この状態に陥っていた。属性に空文字が入りうる経路は塞いでおく。

## 文字列比較は完全一致

`lane_name`のような文字列キーでの照合は完全一致。命名体系が違うジオメトリ同士を突き合わせると、エラーも出ず単に0件になる。

照合が0件のときは「該当が無い」のか「名前の体系が違う」のかを必ず切り分ける。前者は半径やタイミングの問題、後者は**入力ジオメトリを間違えている**ことを意味する。
