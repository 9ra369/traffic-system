# M6: t_ego導入とcross_posのRoad Lineベイク化（2026-09-16）

[[07_RESOLVE_CONFLICT]]のM2判断ロジックを、固定TTC閾値から自車の到達時間との相対比較（M6）に変更し、
その過程で判明した「交錯点座標(`cross_pos`)が特定の直進車個体に依存している」という設計上の脆さを
Road Line側への静的ベイクで解消した（M6b/M6c）。あわせて挙動チューニングと、いくつかの設計確認を行った。

## やったこと

### 1. M6: t_ego導入 — 固定TTC閾値からの脱却
- **課題**：`t_lock = (t_other < decide_ttc)`という固定閾値(3.9s)比較では、自車の状態（停止中か、
  交錯点近くまで進入済みか）を見ておらず、進入済みの車にも一律ブレーキを要求しうる不整合があった。
- **変更**：`blocking = (t_other < t_ego + safety_margin)`に変更。`t_ego`は自車が交錯点に着くまでの
  時間で、走行中は`t_other`と同じ等加速度式、停止中(`car_state>=1`かつ`vel≈0`)は`max_accel`による
  0初速からの到達時間で算出。
- 詳細設計 → [[M6_t_ego]]

### 2. M6b: rt_target_cpの取得元をRoad Line側に変更
- **課題**：交錯点座標(`t_cp`)を、右折車が「今たまたま近くにいる直進車個体」の`cross_pos`から毎フレーム
  読んでいた。対応する直進車がまだ`lane_changed`を済ませていない／近くに1台もいない瞬間に判断が
  不安定になる脆さがあった。
- **変更**：新規[[12_BAKE_CROSS_POS]]で、交錯点座標を道路網生成時にRoad Line側へpoint/prim属性として
  焼き込み。右折車は`cross_lines`確定と同時（`lane_changed`時）に、`lane_id`キーでRoad Line側から
  直接・固定値として`rt_target_cp`を確定するように変更。対応する直進車の有無やタイミングに依存しなくなった。

### 3. M6c: 直進車自身のcross_pos取得も統一
- 直進車が自分のために持つ`v@cross_pos`（M1の`passed`判定用）も、Input 3(歩行者ジオメトリ)への
  `nearpoint`から、同じRoad Line側のベイク値を読む方式に統一。`03_UPDATE_LANE_ATTRIB.vfl`は
  Input 3への依存を完全に無くした。
- **実装中に見つけたバグ**：`s@turn=="straight"`でガードしようとしたが、`lane_changed`ブロック実行時点の
  `s@turn`はまだ前のレーンの値のまま（更新はファイル末尾の毎フレームブロックで、このブロックより後）。
  右折→直進に乗り換えた瞬間だけ`cross_pos`が更新されずに固まるバグになるところだった。ガードを外し、
  右折レーンのprimは単に未設定＝既定値が返るだけ（実害なし）という形に直して回避。

### 4. コミット・push
- ブランチ`feat/m6-t-ego-and-cross-pos-baking`を作成し、上記1〜3をコミット・push済み（`c89565f`）。
  `master`は既定ブランチなので直接コミットしていない。

## 設計上の学び（今回分）

- **「検知」と「判断」はレイヤーが違う**：M2の候補探索(`nearpoints`, 36m半径)は距離ベースの検知で、
  TTCとは無関係。TTC比較（`t_other`/`t_ego`）はロック済みの1台に対してだけ行う判断ロジック。
  「検知が遅い」と感じたら検索半径側、「判断が遅い」と感じたらTTC側、と切り分けて考える必要がある。
- **t_egoには「近づくほど判定が渋くなる」逆説がある**：自車が巡航中のまま交錯点に近づくと`t_ego`
  （自車の到達時間）が縮み、`blocking`の閾値(`t_ego + safety_margin`)も一緒に縮む。本来もっと慎重に
  なるべき局面で判定が発火しにくくなる構造的な副作用。今回は`safety_margin`を1.0→3.0に上げる運用的な
  対処に留めた（下記「保留中」参照）。
- **フレーム内の属性更新順序に注意**：同じwrangle内でも、ブロックの後半でしか更新されない属性
  （`s@turn`など）を、その手前で参照すると前フレームの値（ステイル値）を掴む。`lane_changed`ブロックの
  中で「今のレーンの種別」を条件に使いたい場合は、その場で`point(1,"turn",pt)`のように新しい値を
  明示的に取得するべきで、車自身の属性を信用してはいけない。
- **後続車検知はどこにも存在しない**（意図的な設計）：右折車のM2探索は交錯レーンの最近傍1台しか
  TTC評価しない。前提は「同一レーン内は追い越しが起きない（IDMの車間追従モデルにより順序が保たれる）
  ので最近傍＝最速到達」。また`06_CAR DETECT`も前方専用で、後続車は誰からも検知されない
  （後続車自身が前方検知で反応する、という一方向の仕組みでキューが成立している）。これは
  [[M5_multi_lane_and_queue]]に記録されている右折車側の待ち行列方針と対になる話だが、直進車側の
  待ち行列については明文化されていなかった。

## まだ手を付けていない／保留中の論点

- `safety_margin`を3.0、`stop_margin`を3に手動変更したが（[07_RESOLVE_CONFLICT.vfl](../07_RESOLVE_CONFLICT.vfl)、
  未コミット）、実機での挙動検証はまだ。上記の「近づくほど渋くなる」構造的な副作用への根治策
  （`t_ego`に下限を設ける等）も未実装。
- 直進車側の待ち行列（先頭車の後ろに続く車）を考慮したTTC判定は未実装。「同一レーン内追い越しなし」
  という前提が崩れるケース（車線変更・スポーン位置の乱れ等）への耐性は未検証。
- `cross_lines`（`opp_lane`の出どころ）を`lane_id`ではなく`lane_name`で引きたいという要望が出たが、
  `cross_lines`自体がint配列(`lane_id`)としてHoudini側で既に焼き込まれているため型が合わず、単純な
  差し替えでは済まない。目的（何が不安か）を確認中、方針未決定。
- [[12_BAKE_CROSS_POS]]は、このリポジトリ上のコードとしては書いたが、実際のHoudini道路網生成
  パイプラインにはまだ配線されていない。配線するまでは`cross_pos`が常に既定値`{0,0,0}`になり、
  右折車のM2判断ロジック全体（検知は生きるが判断が壊れる）が機能しない点に注意。
